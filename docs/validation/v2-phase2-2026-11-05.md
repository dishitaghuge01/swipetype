# SwipeType v2 Phase 2 verification — 2026-11-05

**Historical baseline at `1bb12ef`.** Mode failures were subsequently fixed and
rendering CPU reduced; see the [follow-up and CPU convention clarification](v2-phase2-fixes-2026-11-05.md).
The measurements and failures below are retained as the original record.

## Verdict

**Core integration checks passed, but Phase 2 does not yet have a clean sign-off.**
Two mode-synchronization cases failed, and active overlay CPU was substantially
above the build plan's low-single-digit expectation. No production code was
changed to hide or fix these failures.

This is automated desktop integration testing using **synthetic touchpad
contacts**, not a claim that physical swipe accuracy or visual quality has been
verified by a person.

## Environment and scope

- Application source: `1bb12ef` (`master`); production source unchanged.
- Arch Linux, x86_64; kernel `7.2.14-arch1-1`.
- Hyprland `0.57.0`, Wayland; one 1920×1080 output at ~60 Hz, scale 1.
- GPU identified by PCI: Intel Alder Lake-UP3 GT2 [UHD Graphics]. Hardware

- Python `3.14.9`, evdev `2.0.0`, wordfreq `3.1.1`, PyYAML `6.0.3`.
- GTK `4.24.1`, gtk4-layer-shell `1.3.0`, WebKitGTK `2.54.2`,
  PyGObject `3.58.1`, Pycairo `1.29.2`.
- Actual injection backend: `ydotool`, connected to the existing user ydotoold.
- Existing normal daemon remained active throughout: PID `657` before/after.

The harness created a separate real daemon, a protocol-B uinput touchpad, a
throwaway GTK TextView editor, and overlay processes. Private runtime sockets,
configuration, and XDG state directories avoided modifying the normal service,
`config.yaml`, or the user's saved layout. Configuration lookup alone was
redirected to a temporary file. Gestures passed through the actual evdev capture,
segmenter, dictionary/scorer, injector subprocess, and desktop text field.

For functional tests, an overlay subclass added DOM observation and a test-only
JavaScript command channel; production event handling and rendering were retained.
**Performance used the uninstrumented production overlay, with dev mode off.**
Focus guards checked the disposable editor before synthetic gestures/clicks.
This still requires an unattended/disposable desktop session: there is a small
race between a focus check and later injected input.

### Reproduced bug: mode is not synchronized on connect/reconnect

Two explicit assertions failed:

1. **Late overlay startup:** daemon was already in swipe mode; a new overlay
   connected, but stayed at `idle` instead of `swipe`.
2. **Daemon restart:** old daemon was in swipe mode when stopped. Overlay
   remained at `swipe` during disconnection and after the replacement daemon
   started in `idle`; expected overlay state was `idle`.

After the next mode toggle, events and typing worked. Thus transport reconnect
works, but state synchronization is incomplete. The broadcaster sends mode only
on changes, not an initial snapshot to new clients; the overlay also retains the
last mode after EOF. Both observations match the implementation.

The harness explicitly toggled off/on after reproducing late-start failure so
that subsequent independent checks could continue; this workaround is not a fix.

Recommended follow-up: retain authoritative mode in the broadcaster and send a
snapshot on each connection, with ordering/thread-safety considered. Consider
hiding/resetting the overlay on disconnect as well. Re-run both assertions after
implementation.

## Performance

Measured with the existing `scratch/measure_overlay.py`, 10-second windows.
The keyboard was visible and swipe mode on in both conditions. Idle means no
contact; active used 17 consecutive synthetic `hello` gestures, 70 points each,
~8 ms between points and a short gap between words. These are repeatable ideal
paths, not measured human swiping behavior.

| Condition | Process-tree PSS | Process-tree CPU |
|---|---:|---:|
| Idle, visible keyboard | 285.0 MiB | 0.0% |
| Continuous synthetic swiping | 301.4 MiB | 59.8% |

Active breakdown: overlay Python **15.1%**, WebKit web process **44.7%**.
A preceding corrected run measured **284.1 MiB / 0.0% idle** and
**303.9 MiB / 65.6% active**, so elevated active CPU reproduced.

Interpretation:

- The script prints `MB`, but divides KiB by 1024; these values are MiB.
- PSS apportions shared pages; it is not RSS. No idle RSS claim is made.
- 59.8% means approximately 0.598 CPU cores, not 59.8% of all laptop cores.
- Figures cover the overlay process tree, not daemon/editor/compositor CPU or
  GPU utilization. They are not total-system input-method cost.
- Idle behavior is consistent with stopping the animation loop.
- Active behavior **does not meet Phase 2h's low-single-digit expectation**.
  Profile the Python→JS flushes, canvas rendering and graphics backend before
  choosing an optimization; the measurements alone do not establish the cause.
- GTK emitted Vulkan initialization warnings; theme imports also referenced
  missing local CSS files. The UI still loaded and tests ran. These warnings
  are retained in the logs rather than presumed to explain the CPU cost.

## Still requires human validation

- Real finger swipes and natural one-/two-finger flicks on the physical touchpad.
- Recognition accuracy across a representative vocabulary, not ideal templates.
- Visual transparency, comet smoothness/lag, and whether it feels responsive.
- Physical drag/corner resize/toolbar operation. Persistence and corruption
  recovery were checked via the real JS bridge, not physical dragging.

No pass is claimed for those manual observations. X11, other compositors,
other GPUs, and installed-package behavior were not tested here.

## Documentation deviations to reconcile

These are implementation choices, not newly discovered runtime failures:

- `toggle-overlay` is context-sensitive; original PRD examples still use `layout`.
- Word flash is intentionally disabled in JS; PRD/build-plan checks still ask
  for it. Record acceptance of the removal or restore it.
- Keeping the native window mapped and using opacity is the PRD S6 fallback.
- The tested host ctypes-loads layer-shell before GTK; do not blindly enable
  `LD_PRELOAD` in a future packaged launcher.
